# AgentAgency — 제품 요구사항 문서 (PRD)

- 제품명: **AgentAgency**
- 태그라인: **Your Agents. Your Agency.**
- 구현 현황: [요구사항별 구현 상태](../requirements-status.md)

## 1. 제품 비전과 범위

AgentAgency는 사용자가 AI 에이전트 조직을 구성하고 목표를 지시하면, 진행자 AI와 개별 에이전트가 Telegram에서 실제로 토론·분업·실행·검증·보고하는 **오픈소스 자체 호스팅 멀티 에이전트 운영 플랫폼**이다. 사용자는 최고 의사결정자이며, AI는 승인된 범위 안에서 자율적으로 일한다. 초기 업무 유형은 소프트웨어 개발(Coding Agency)이다. 향후 조사·분석·콘텐츠 등 업무 유형을 확장할 수 있도록 코어와 업무 플러그인을 분리한다.

### 1.1 제품 가치
1. **조직 경험**: AI를 단순 호출하지 않고 조직 구성원처럼 관리한다.
2. **보이는 협업**: 실제 의미 있는 AI 간 의견 교환과 역할 조정을 Telegram Topic에서 확인한다.
3. **실제 산출물**: 코드, 테스트, GitHub PR, 프리뷰 링크, 문서, 의사결정 이력으로 결과를 남긴다.
4. **통제 가능한 자율성**: 고위험·범위 확대·비용·운영 변경은 사용자 승인 후 실행한다.
5. **구독 우선**: 공식 지원 범위의 구독 인증 실행기를 우선 사용하고 유료 API로 자동 전환하지 않는다.

### 1.2 대상 사용자
- 개인 개발자 및 AI 코딩 도구 유료 구독자
- 소규모 팀/개인 프로젝트 운영자
- 자체 서버에 Docker로 설치하고 Telegram으로 관리하려는 사용자

### 1.3 초기 비목표
- 모든 AI 공급자의 구독 세션을 무조건 자동화할 수 있다고 가정하지 않는다.
- 실제 인간 직원의 법적 고용·계약·인사관리를 구현하지 않는다.
- 초기 MVP에서 일반 업무 에이전시 전체를 제공하지 않는다.
- 조직 세계관에 따라 보안·승인·테스트 기준을 낮추지 않는다.

## 2. 사용자별 조직 세계관

사용자는 자신의 마스터 라운지에 적용할 조직 모드를 선택한다. 조직 모드 변경 시 프로젝트·작업·에이전트 정체성·기억은 유지하고 표현 레이어만 전환한다.

| 모드 | 사용자 | 진행자 AI | 에이전트 | 기본 분위기 |
|---|---|---|---|---|
| Corporate / 회사 | CEO | 수석비서 | 팀장 | 정중한 보고·회의·조율 |
| Construction / 노가다 | 건물주 | 십장(현장반장) | 현장 작업자 | 현장감·유머·실행 중심 |
| Campus / 대학 조별과제 | 교수 | 조교 | 학생 | 조별 토론·질문·발표 |

### 2.1 확정 AB 정책
- **A 기본**: 세계관·호칭·말투·캐릭터 표현만 변경한다. 실제 작업 프로세스는 동일하다.
- **B 선택형 실험**: 모드별 보고·토론·협업 스타일을 변화시키는 기능은 플래그 뒤에 구현한다. 효용성 검증 전 기본 비활성화.
- 어떤 모드에서도 품질 게이트, 보안, 승인, 실행 권한, 비용 제한은 동일하다.

### 2.2 관계 인식형 대화(Role-aware Dialogue)
메시지 생성은 단일 고정 말투가 아니라 **세계관 + 발화자 + 청자 + 상황 + 친밀도 + 페르소나**를 사용한다.

| 모드 | 발화자→청자 | 말투 정책 예시 |
|---|---|---|
| 대학 | 학생→교수 | 격식 있는 존댓말, 결과·근거 보고 |
| 대학 | 학생→조교 | 자연스러운 존댓말, 질문·도움 요청 |
| 대학 | 학생→학생 | 친근한 반말 가능, 동등한 협업 |
| 회사 | 팀장→CEO | 정중한 존댓말과 의사결정 보고 |
| 회사 | 팀장→팀장 | 동료 간 존댓말, 직무 협업 |
| 노가다 | 작업자→건물주 | 친근한 존댓말, 진행 보고 |
| 노가다 | 십장→작업자 | 현장식 직접 지시, 모욕·차별 금지 |
| 노가다 | 작업자→작업자 | 편한 반말·유머 가능 |

규칙:
- 다수 수신자가 있는 메시지는 명시된 청자를 우선하며, 불분명하면 공용방 기준의 안전한 말투를 사용한다.
- 조직 내 역할·예의는 유지하되 동료 간 친밀도는 협업 경험에 따라 점진적으로 변할 수 있다.
- 친밀도는 **표현에만** 영향을 주며 권한·품질·업무 배정·승인에는 영향을 주지 않는다.
- 말투 생성이 기술적 사실을 바꾸거나 실행 결과를 꾸며내서는 안 된다.
- 사용자/AI 간 조롱, 비하, 욕설 남발은 제한한다.
- 캐릭터 메시지와 기계 판독 가능한 실행 상태는 별도 데이터 구조로 관리한다.

## 3. 에이전트 모델

에이전트는 특정 AI 모델과 동일하지 않은 **지속적 정체성**이다.

### 3.1 구성 요소
- `agent_id`: 불변 내부 식별자
- `name`: 표시 이름
- `provider`: Anthropic/OpenAI/Google 등
- `executor_adapter`: 공식 지원 클라우드 세션 또는 구독 인증 CLI 어댑터
- `model_selection`: `auto` 또는 공식적으로 지원·확인된 모델 식별자
- `persona`: 성격 프리셋 및 선택적 사용자 지침
- `organization_role`: 세계관에 따른 역할
- `functional_role`: 실제 업무 역할(리더·구현·리뷰·테스트 등), 작업별 변경 가능
- `relationships`: 다른 에이전트와의 관계·친밀도 메타데이터
- `memory_ref`: 프로젝트별 관련 결정·작업 이력·인계 메모리
- `capabilities`: 지원 기능, 실행/취소/재개/사용량 확인 가능 여부
- `look`: 표현용 캐릭터(모양·색·소품). 표정으로 지금 하는 일을 보여 주며 권한·배정과 무관하다

### 3.2 확정 예시
```yaml
agent:
  id: agent-001
  name: 클로드
  executor:
    provider: anthropic
    model: auto
    auth_mode: official_subscription
  persona:
    preset: careful
    custom_instructions: null
  organization:
    role: auto
    dialogue_policy: relationship_aware
  memory:
    enabled: true
    relationship_history: true
```

- 성격 `careful`은 꼼꼼한 완벽주의자라는 **연출 지침**이지 모델의 객관적 능력을 의미하지 않는다.
- 모델을 교체해도 이름·페르소나·관계·프로젝트 기억을 유지한다.
- 같은 모델을 여러 에이전트가 사용할 수 있다.
- 모델 선택 `auto`는 인증된 실행기에서 지원하는 가용 모델만 고려한다. 미지원 모델이나 유료 API로 자동 전환하지 않는다.
- 모델별 고유 표현·문제 해결 스타일은 존중하되, 업무 정확성과 사용자 명시 지시가 캐릭터 연출보다 우선한다.

## 4. 사용자 경험 및 Telegram 정보 구조

### 4.1 마스터 라운지
- 사용자별 운영 모드 및 진행자 AI를 선택한다.
- 사용자의 자연어 지시를 진행자가 해석하고 관련 AI 1~3명을 소집한다. 명시적 @멘션을 우선한다.
- 기본 토론은 최대 3라운드, 합의 시 조기 종료하며 사용자 요청 시 연장 가능하다.
- 신규 프로젝트는 이름·기술 스택·AI 팀·비공개 GitHub 저장소 생성안을 제시하고 사용자 승인 후 생성한다.
- `/status`는 모든 프로젝트의 진행 상태·현재 작업·담당 AI·대기 승인을 요약한다.

### 4.2 프로젝트 Topic
- Telegram 단일 봇이 모든 AI 메시지를 전송하며 AI 이름·역할·발화 대상을 표시한다.
- 실제 의미 있는 AI 대화는 공개하되 명령어·전체 터미널 로그·비공개 추론은 스트리밍하지 않는다.
- 고정 진행 메시지 하나를 갱신해 단계(요구사항→구현→테스트→리뷰→수정→PR), 담당 AI, 현재/최근 완료 작업, 차단 사유를 표시한다.
- 중요한 승인·결정·완료 보고는 별도 메시지와 인라인 버튼으로 처리한다.
- 사용자가 특정 AI를 @멘션하면 해당 AI를 우선 배정하되 리더가 우선순위와 충돌을 조율한다.
- 자연어 명령 및 승인/수정/취소/중단/재개/우선순위 버튼을 지원한다.
- 사진·문서·음성 입력은 연결 실행기가 공식 지원하는 범위에서 분석/전사하며 외부 입력은 신뢰하지 않는다.

### 4.3 보고 카드
- 구현 기능·변경 내용·테스트·리뷰·PR·프리뷰 URL·미해결 이슈를 구조화해 표시한다.
- 주요 기능·UX·프로젝트 완료는 사용자 최종 확인이 필요하다.
- PR 병합과 운영 배포 승인은 별도로 관리한다.

## 5. Coding Agency 업무 흐름

1. **요청 이해**: 명확한 지시는 작업화, 단순 아이디어는 후보 목록에 저장, 중요한 모호성만 질문한다.
2. **기획**: 프로젝트 리더가 PRD·아키텍처·작업 계획·수용 기준을 AI 팀과 구성한다. 주요 범위/아키텍처는 사용자 승인.
3. **배정**: 작업 난이도·성공률·가용 구독·의존성·충돌 위험을 고려해 개발/리뷰/테스트 역할 배정.
4. **실행**: 분리된 Docker 워크스페이스 또는 검증된 공식 클라우드 실행기에서 수행. 작업별 Git 브랜치 사용.
5. **협업**: AI 간 이견·막힘·API 변경·충돌을 Topic에서 조율하고 필요한 맥락만 다른 AI에 전달.
6. **검증**: 테스트·lint·타입·보안 검사·교차 리뷰·브라우저(Playwright) 시나리오 검증.
7. **수정**: 제한된 자동 재시도/재검증. Flaky Test는 재실행·로그·스크린샷 비교로 원인 규명 후 품질 게이트 재실행.
8. **PR/프리뷰**: 검증된 GitHub PR 생성, 가능한 웹 프로젝트는 프리뷰 배포와 스크린샷 제공.
9. **승인/완료**: 사용자 승인 정책에 따라 병합 및 운영 배포, 결과 보고, 문서/메모리 업데이트.
10. **사후관리**: 배포 상태 감시, 오류 조사, 보안/의존성 유지보수 작업을 저우선순위로 처리. 운영 재배포는 승인.

### 5.1 승인 레벨
- 기본: 승인된 목표 범위 내 자율 실행, PR 병합은 사용자 승인.
- 주요 아키텍처·새 기능/범위·보안·비용·운영 DB 변경·운영 배포·파괴적 작업은 별도 승인.
- 핵심 기능·중대한 UX 변경·프로젝트 전체 완료는 사용자 최종 확인.
- 사용자 선택으로 더 엄격한 승인 모드 또는 허용 범위 내 완전 자동 모드를 제공할 수 있다.
- 명시적 중단은 가능한 실행기에서 실제 취소를 시도하고 상태를 확인한다. 공식 취소 불가능한 실행기는 한계를 명확히 알린다.

### 5.2 기존 프로젝트 가져오기
기존 GitHub 저장소를 **읽기 전용**으로 분석해 구조·스택·문서·테스트·CI를 파악하고 프로젝트 요약/AI 팀 구성안을 제안한다. 사용자 승인 후 Topic과 연결한다. 가져오기 과정에서 기존 코드를 임의 변경하지 않는다.

### 5.3 프로젝트 수명주기
`proposed → active → paused/blocked → completed → archived`를 기본으로 하며 보관 후 복원 가능하다. 보관 시 실행 자원을 정리하되 GitHub/Topic/핵심 메모리를 유지한다. 영구 삭제는 내부 데이터와 외부 자원을 분리해 명시적 재확인을 요구한다.

## 6. 시스템 아키텍처

```text
Telegram (single bot; master lounge + project topics)
                |
        Telegram Gateway
                |
        Orchestration Core
    ┌───────────┼────────────┐
    |           |            |
 Project/Task  Agent Team   Approval/Policy
 Manager       Coordinator  Engine
    |           |            |
    └───────────┼────────────┘
                |
        Execution Scheduler
                |
      Executor Adapter Layer
       /         |         \
 Claude official Codex official Future adapters
 subscription   subscription (Gemini, etc.)
 session/CLI    session/CLI
                |
   Isolated workspace / vendor cloud
                |
     GitHub + CI + Preview services
                |
    Project Memory / Audit / Secrets
                |
          PostgreSQL + files
```

### 6.1 필수 컴포넌트
1. **Telegram Gateway**: 사용자 ID 인증, 메시지/콜백 라우팅, Topic/고정 메시지 관리.
2. **Orchestration Core**: 요청 분류, 프로젝트/작업 상태기계, 리더 조정, 재시도·체크포인트.
3. **Dialogue Renderer**: 세계관·발화자·청자·관계·페르소나를 적용해 사용자 표시 메시지 생성. 실제 실행 지시와 분리.
4. **Agent Registry**: 정체성, 모델 선택, 페르소나, 역할, 능력, 관계 기록.
5. **Executor Adapter**: 인증 상태, 실행, 결과 수집, 공식 지원 범위 내 취소/재개, 사용량/쿼터 신호.
6. **GitHub Integration**: repo/branch/commit/PR/검증 링크와 소스의 진실 원천.
7. **Quality Gate**: 테스트·lint·타입·보안·교차 리뷰·Playwright.
8. **Approval Engine**: 요청자·프로젝트·작업·만료와 연결된 승인 상태, 위험 등급.
9. **Memory & Audit**: 요구사항·결정·작업·인계·실패 교훈·관계 변화, 민감정보 마스킹.
10. **Secrets & Security**: 암호화 저장, 최소 권한 주입, 네트워크 제한, 인증 폐기·격리.

## 12. 핵심 수용 기준

1. 사용자는 회사/노가다/대학 모드를 선택하고 같은 요청에 대해 **상대 관계에 맞는** 다른 표현을 확인할 수 있다.
2. 에이전트의 이름·모델·성격을 변경해도 프로젝트/작업/관계 기록은 유실되지 않는다.
3. 단일 Telegram 봇에서 AI별 이름·역할·발화 대상이 식별되고 실제 협업 내용이 보인다.
4. 승인된 개발 요청이 GitHub PR과 테스트 결과로 귀결되며 코드 변경은 추적 가능하다.
5. 중요 승인 없이 운영 배포·운영 DB 변경·비용 발생·영구 삭제가 실행되지 않는다.
6. 구독 실행기가 불가능하거나 공식 지원되지 않는 기능은 사용자에게 정확히 표시하며 유료 API로 자동 전환하지 않는다.
7. 비밀정보는 Telegram·GitHub·실행 로그에 노출되지 않고 사용자별/프로젝트별 접근 권한이 검증된다.
8. 서버 재시작/업데이트 후 체크포인트와 승인 상태를 복구하고 중복 외부 작업을 방지한다.
9. 모드별 말투/친밀도 변화가 실행 정책과 품질 게이트를 바꾸지 않는다.
10. 기존 GitHub 프로젝트는 읽기 전용 분석과 사용자 승인 후에만 관리 대상으로 연결된다.

## 13. 기술 선택

- 백엔드: TypeScript(ESM), Node.js 22. 웹 서버는 Hono, Telegram은 grammy(Long Polling), GitHub는 Octokit.
- DB: PostgreSQL을 기억·대화·작업 상태의 원천으로 쓴다(§17). 개발·테스트에는 내장 PostgreSQL(PGlite)을 쓴다.
- 큐·스케줄러: PostgreSQL 기반 작업 큐(`FOR UPDATE SKIP LOCKED`)와 자원 인식 스케줄러.
- 실행기: 공식 구독 CLI(Claude Code, Codex, Gemini, Cursor)를 어댑터로 연결한다. 클라우드 실행기는 실제 검증 기록이 있을 때만 자동 선택한다.
- 격리: 프로젝트별 비루트 Docker 컨테이너(`--cap-drop ALL`, `no-new-privileges`, CPU·RAM·pids 제한, 네트워크 선택).
- GitHub 연결: 개인 계정은 Fine-grained PAT, 조직은 GitHub App(최소 권한).
- Telegram 구조: 사용자별 마스터 라운지(포럼 그룹)와 프로젝트별 Topic.
- 말투 렌더러: 템플릿 기본, LLM 다듬기는 사실 보존 검증·캐시를 갖춘 선택 기능.

## 14. 설계상 주의사항

- 이 문서는 제품 요구사항과 논리 아키텍처를 확정하는 것이며, 모든 공급자 기능의 실제 지원을 보증하지 않는다.
- **공식 구독 인증으로 수행할 수 없는 자동화는 우회 쿠키 추출이나 무단 API 전환으로 구현하지 않는다.**
- 캐릭터 성격·친밀도는 사용자 경험용 메타데이터로, AI 모델의 고정된 객관적 성격을 주장하지 않는다.
- 외부 서비스의 변경·삭제·운영 반영은 승인과 최소 권한 정책을 따른다.

## 15. 실행 정책: Cloud First → 격리된 Local CLI

- 기본 실행 순서는 **공식 구독 기반 Cloud → Local CLI Fallback**이다. 사용자별 기본값을 저장하고 프로젝트별·에이전트별로 재정의할 수 있게 한다.
- 우선순위와 자동 전환 여부를 설정할 수 있어야 한다. Cloud 실행 불가, 구독 한도 소진, 인증 만료 시 사용 가능한 다른 공식 구독 실행기 또는 격리된 Local CLI로 전환한다.
- **종량제 유료 API는 기본 비활성화하며 자동 전환하지 않는다.** 사용하려면 사용자의 명시적 승인이 필요하다.
- 구독 보유와 외부 자동화 지원을 구분한다. 제공업체별 공식 문서와 실제 연동으로 구독 적용 범위, 인증 방식, 작업 생성·상태 조회·결과 수집 지원 여부를 검증한다. 취소·재개 미지원 등 제약을 표시한다.
- 공식 지원이 확인되지 않은 Cloud 연동을 사용 가능으로 표시하지 않는다. 지원되는 로컬 방식만 활성화하고 사유를 안내한다. 인증 우회나 비공식 세션 자동화는 구현하지 않는다.
- Fallback 전에 기존 외부 작업의 종료 여부를 확인하여 중복 실행을 방지한다. GitHub와 AgentAgency 체크포인트로 작업 맥락을 복원한다.
- Local CLI는 실행 서버의 Docker 격리 환경에서 CPU/RAM 및 동시 실행 제한을 적용한다.

```yaml
execution:
  priority: [cloud, local_cli]
  auto_fallback: true
  paid_api:
    enabled: false
    require_explicit_approval: true
  overrides:
    per_project: true
    per_agent: true
```

## 16. 클라우드 중립 배포와 자원 관리

- **Docker Compose 기반 단일 Linux 서버 배포**를 기본으로 한다. OCI, AWS EC2, Azure VM, GCP Compute Engine, 일반 VPS, 온프레미스 Linux 서버에서 설치 가능해야 한다. Kubernetes는 필수가 아니다.
- OCI Always Free는 초기 운영·테스트 및 비용 최적화 대상일 뿐 필수 인프라가 아니다. 핵심 기능이 OCI SDK/API나 특정 제공업체 관리형 서비스에 의존하지 않도록 한다.
- PostgreSQL, 작업 큐, 파일 저장소, 실행기는 교체 가능한 구조로 구성한다. 클라우드별 기능·최적화는 선택형 어댑터 또는 별도 배포 프로파일로 분리한다.
- Cloud First 정책은 설치된 인프라 제공업체와 무관하게 동작해야 한다. AI Cloud 실행기와 서버 호스팅 클라우드를 구분한다.
- 서버는 Telegram Bot, 오케스트레이터, 큐·스케줄러, PostgreSQL, 설정·관계·컨텍스트·연결 관리, 상태 모니터링을 담당한다.
- 실제 CPU/RAM/디스크를 감지해 동시성과 로컬 작업량을 조절한다. 무거운 빌드·테스트는 가능한 경우 공식 Cloud 실행기 또는 GitHub Actions에 배치하되, 사용량과 별도 과금 가능성을 확인한다.
- 제공업체를 바꾸어도 설정·에이전트·기억·프로젝트 데이터를 백업·복원하여 이전할 수 있어야 한다.

## 17. 영구 기억·문서·파일 저장

**PostgreSQL을 에이전트 대화와 기억의 Source of Truth로 사용한다.** Telegram 기록이나 개별 AI 세션의 기억에만 의존하지 않는다.

| 데이터 | 저장 위치 |
|---|---|
| 에이전트 간 원본 대화 이벤트, 요약, 확정 결정 | PostgreSQL |
| 에이전트 이름·모델·페르소나, 관계·친밀도 | PostgreSQL |
| 프로젝트 기억·선호도, 작업 상태·체크포인트 | PostgreSQL |
| 코드·PRD·설계·결정 문서, PR·테스트 정의 | GitHub |
| 실행 로그·스크린샷·첨부·임시 실행 파일 | 배포 환경의 파일 저장소 |

- 원본 대화와 구조화된 기억을 분리하고, 요약·결정에 근거 대화 또는 작업 ID를 연결한다. 확정 결정과 제안·추측을 구분한다.
- 새로운 명시적 사용자 지시를 기존 기억보다 우선한다. 모델·실행 환경 변경 후에도 정체성·관계·기억을 유지한다.
- 프로젝트별 비공개 맥락을 격리한다. 관계·친밀도는 대화 표현에만 반영하고 접근 권한에는 영향을 주지 않는다.
- DB는 영구 볼륨에 저장한다. 자동 백업과 복구를 지원하고 컨테이너 재생성·서버 이전 후 데이터 유지 및 복원을 검증한다. 외부 객체 저장소 백업은 선택 사항이며 OCI에 종속시키지 않는다.
- 오래된 로그·임시 파일을 자동 정리한다. 보관 기본값은 실행 로그 30일, 임시 파일 7일로 두고 설정 가능하게 한다.
- MVP는 PostgreSQL로 시작한다. pgvector 기반 의미 검색은 후속 선택 기능이다.

### Context Builder

AI 세션 시작·재개 시 현재 작업에 필요한 정보만 선택하여 전달한다.

1. 에이전트 정체성·페르소나, 조직 세계관·역할, 상대별 말투 정책
2. 프로젝트 목표·확정 결정, 담당 작업·수락 기준
3. 관련 최근 대화·요약 및 에이전트 간 협업 이력
4. 관련 GitHub 브랜치·PR·테스트 결과 및 체크포인트

전체 대화를 매번 주입하지 않으며, 실행기를 바꿀 때에도 같은 저장소에서 맥락을 재구성한다.

## 18. 설치와 초기 설정

설치부터 운영 시작까지 하나의 터미널 흐름으로 끝난다. 브라우저나 공개 도메인이 필요 없다.

1. `install.sh`: 서버 확인 → Docker(없으면 설치) → 코드 받기 → `.env`와 비밀번호 자동 생성 → 빌드·실행
2. Telegram Bot 토큰 등록과 연결 테스트, 그룹·관리자 자동 감지, 봇 권한 진단
3. Claude/Codex/Gemini 등 공식 구독 로그인과 실제 실행 검증
4. GitHub 연결(PAT 또는 GitHub App) 또는 건너뛰기
5. 기본 실행 우선순위, 조직 세계관, 초기 에이전트(이름·성격·모습)
6. 전체 연결 진단과 엔드투엔드 스모크 테스트 → Telegram 운영 시작

- 이후 모든 설정은 `aa config`(터미널 메뉴) 또는 Telegram에서 바꾸며 서버 파일을 반복해서 고치지 않는다. 바뀐 설정은 실행 중인 서비스에 즉시 적용한다.
- 운영 관리(상태·로그·진단·백업·업데이트·재시작)는 `aa` 메뉴로 한다.
- 연결 상태·인증 만료·사용 가능 실행기·오류와 미지원 사유를 확인할 수 있게 한다.
- 초기 구성은 Telegram Long Polling을 쓴다. OAuth 콜백·웹훅이 필요한 연동만 HTTPS 공개 URL을 설정한다. 웹 대시보드는 선택 사항이며 서버 내부(127.0.0.1)에만 열고 SSH 터널로 접속한다.
